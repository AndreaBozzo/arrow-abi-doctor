# M0.5 verification record — smoke

M0.5 asks for one thing: an adapter for `dataprof`, an existing C Data / C Stream
consumer under our own control, to validate `libabi` and the lifecycle
scaffolding.

It is explicitly **not a differential pair**. It is the test of the instrument.
A disagreement here is far more likely to be our bug than the consumer's, which
is exactly why the first target is one we own.

---

## What M0 left unbuilt

M0 produced a portable *description* of a case and verified it round-trips
byte-for-byte across architectures. It never turned one back into an
`ArrowSchema` or `ArrowArray`. Nothing can consume a description, so the first
half of M0.5 is the reconstructor.

## What was built

| Component | Purpose |
|---|---|
| `libabi/include/abi/arrow_abi.h` | the C Data / C Stream structures, vendored verbatim |
| `libabi/src/reconstruct.c` | `.abicase` → real `ArrowSchema` / `ArrowArray` |
| lifecycle observer (same file) | instrumented allocator, ordered event log, release-depth attribution |
| `adapters/dataprof/abicase_py.c` | CPython extension presenting a case as an Arrow PyCapsule producer |
| `adapters/dataprof/run_smoke.py` | the harness and its report |
| `adapters/dataprof/repro_findings.py` | standalone reproducers, no libabi dependency; now regression checks against the fixes |

### Three things in the reconstructor that are easy to get subtly wrong

**Aliasing is physical.** One real allocation per `AbiAllocation`; views are
pointers into it. Two buffers the case says alias come back as the *same
address*, verified by pointer comparison rather than by comparing contents.
Equal contents would silently satisfy a weaker test while testing nothing.

**Metadata is written in native byte order.** That is the opposite of the file
format's every-integer-is-little-endian rule, and it is deliberate: Arrow's
metadata wire form uses native-endian `int32`, so this buffer has to match the
host the consumer runs on. It is the reason `.abicase` stores metadata decoded
into key/value pairs in the first place. The big-endian test run is the only
place that half of the encoder is actually exercised.

**Release frees what was allocated, not what was declared.** A B1 case may
declare `n_children = 5` while providing 2. The extra slots are real,
NULL-initialized pointers, so a consumer walking `n_children` dereferences a
NULL — the defect under test, unambiguously in the consumer. Allocating only the
provided count would instead have the consumer read past *our* array, making the
fault ours and aborting the harness under a sanitizer before the consumer was
ever reached. The slot count therefore lives in `private_data`, not re-derived
from the struct the consumer can see.

## Lifecycle observation

Counters cannot distinguish these two:

```
consumer -> parent.release() -> producer -> child.release()   CORRECT
consumer -> child.release()                                   VIOLATION
```

So every event carries the nesting depth of the producer's own release
callbacks. A release entered at depth 0 was entered from outside; a *child*
release entered at depth 0 is the violation, observed rather than deduced. The
log for the rich fixture:

```
000 SCHEMA_EXPORTED            /
001 ARRAY_EXPORTED             /
...
010 ARRAY_RELEASE_ENTER        /          <- entered by consumer
011   ARRAY_RELEASE_ENTER        /0/
012   ARRAY_RELEASE_EXIT         /0/
013   ARRAY_RELEASE_ENTER        /1/
014     ARRAY_RELEASE_ENTER        /1/dict/
015     ARRAY_RELEASE_EXIT         /1/dict/
016   ARRAY_RELEASE_EXIT         /1/
017 ARRAY_RELEASE_EXIT         /          <- entered by consumer
ALLOC_DELTA  0 bytes / 0 blocks
violations:  0
```

Allocation counts come from an instrumented allocator with a size header on
every block. Without one, "0 leaks" is declared, not measured.

## Results

`libabi` tests: **123 format checks + 73 reconstruction checks, 0 failures**, on
all three platforms including s390x big-endian. Clean under ASan, UBSan, and
Valgrind with `--leak-check=full --errors-for-leak-kinds=all`.

Smoke run, three fixtures × three consumer paths. Both findings below have since
been fixed upstream, so the table has a before and an after; the only variable
between them is the dataprof wheel — same libabi, same fixtures, same pyarrow
25.0.1, same host.

Against dataprof **0.10.0** (published wheel, and a build of master content at
`3a2b1fd` — identical results):

| Fixture | pyarrow | dataprof direct | dataprof via pyarrow |
|---|---|---|---|
| `smoke` — struct<int32, utf8> | accepted, 4×2 | rejected (type gate) | accepted |
| `rich` — alias, misalignment, dictionary, metadata | accepted, 8×2 | rejected (type gate) | accepted |
| `bad-dict-index` — class B1 | accepted, 4×1 | rejected (type gate) | **panic** |

Against dataprof **master `0ca2766`** (2026-08-20), which carries both fixes:

| Fixture | pyarrow | dataprof direct | dataprof via pyarrow |
|---|---|---|---|
| `smoke` — struct<int32, utf8> | accepted, 4×2 | accepted | accepted |
| `rich` — alias, misalignment, dictionary, metadata | accepted, 8×2 | accepted | accepted |
| `bad-dict-index` — class B1 | accepted, 4×1 | **clean `ValueError`** | **clean `ValueError`** |

The type gate is gone, so the third column no longer has a confound to remove —
and the B1 case now produces the outcome the class was written to demand: a
refusal that names the violated invariant, on both paths.

```
ValueError: Arrow data received over the C Data Interface violates the Arrow
columnar spec and cannot be profiled: Invalid argument error: Value at
position 2 out of bounds: 99 (should be in [0, 1])
```

pyarrow still accepts that array on import. That is consistent with its
documented zero-copy, opt-in-validation behaviour, and it is now a *live*
disagreement between two consumers over the same bytes rather than a
hypothetical one — the shape M1 is built to find systematically.

**9 runs on each wheel, 0 leaks, 0 lifecycle violations, on both.** Every capsule
the consumers took was released by the consumer; every case the consumers
declined was cleaned up by the harness and logged as such. That held across a
type rejection, a panic and a validation error — three different ways for a
consumer to not finish — which is the property the instrument is being smoked
for.

The third column existed to remove a confound. A rejection alone cannot be
attributed to either side; the same data accepted when wrapped in a pyarrow
`RecordBatch` said the reconstruction was well-formed and the refusal was about
the *type of Python object*, not the bytes. It is what made finding 1 reportable
rather than a suspicion about our own producer.

## Findings

Both surfaced while exercising dataprof, both were filed, and **both are now
fixed on dataprof master.** The discipline the project's own framing demands
applied to both: a finding is worth an issue only once it is confirmed against
the code that will ship, with a reproducer that does not depend on this tool
wherever one exists. The smoke run used the published 0.10.0 wheel; 0.10.0 was
65 commits behind master, so the wheel proved nothing on its own. Confirmation
and resolution status are stated per finding.

| # | Filed | Fixed by | On master |
|---|---|---|---|
| 1 | [dataprof#608](https://github.com/AndreaBozzo/dataprof/pull/608) | `fa1aa7d` | 2026-08-20 |
| 2 | [dataprof#609](https://github.com/AndreaBozzo/dataprof/issues/609) | [#610](https://github.com/AndreaBozzo/dataprof/pull/610), `0ca2766` | 2026-08-20 |

### 1. A non-pyarrow Arrow PyCapsule producer is refused

`profile()` documents support for "Arrow PyCapsule-compatible objects", and the
Python layer routes anything with `__arrow_c_array__` to `_profile_arrow`. But
`profile_arrow` calls `import_from_pyarrow` directly — commented "no library
detection needed" — and that function gates on the Python type name being
`Table` or `RecordBatch`. The duck-typed branch that would call
`import_via_pycapsule` exists but is not reachable from this path.

Verdict, per the project's own matrix: a clean rejection whose limitation is not
merely undocumented but contradicted by the documentation. A **documentation
gap**, and arguably a plain bug, since the supporting code is present and
bypassed.

**Status: confirmed on master.** Reproduced against a wheel freshly built from
the working tree at `3a2b1fd`, whose `arrow_export.rs` and `__init__.py` are
byte-identical to `origin/master` (`f0fb590`). The reproducer
(`repro_findings.py`) uses only pyarrow: a wrapper object delegating
`__arrow_c_array__` to a `RecordBatch` is refused while the `RecordBatch`
itself is accepted, which isolates object type as the single variable.

```
[ ok   ] control: dataprof.profile(pa.RecordBatch)
[reject] under test: dataprof.profile(PyCapsuleProducer)
         TypeError: Expected pyarrow Table or RecordBatch, got PyCapsuleProducer
```

**Resolved by [dataprof#608](https://github.com/AndreaBozzo/dataprof/pull/608)
(`fa1aa7d`), verified here.** Acceptance now matches the *API* — an object
carrying `to_batches` / the PyCapsule dunders — rather than the Python type
name, which was Copilot's point in review and the right one: gating on
`type(obj).__name__` contradicts an "any producer" contract by construction.
Re-running the same reproducer against a wheel built from `0ca2766` accepts the
producer; against the 0.10.0 wheel it still refuses, so the check discriminates
rather than merely passing. The same PR also fixed a chunked `Table` being
profiled over its first batch only — a silent divergence, found alongside.

### 2. An out-of-range dictionary index panics

A `dictionary<int8, utf8>` whose index is 99 over a two-value dictionary makes
profiling raise `PanicException: Trying to access an element at index 99 from a
StringArray of length 2`.

The input **is invalid** — an out-of-range dictionary index violates the
columnar specification — so a refusal is the correct outcome. The finding is
that the refusal arrives as a Rust panic crossing the FFI boundary rather than
as an error. pyo3 derives `PanicException` from `BaseException` specifically so
it is not caught by accident, so a caller doing `except Exception` does not
catch it. This is a robustness defect, not memory unsafety.

**Status: confirmed on master.** Reproduced against a Linux wheel built from the
working tree at `3a2b1fd`, byte-identical to `origin/master` for the files
involved. Identical message on the 0.10.0 wheel and on the master build.

**Where the panic actually comes from.** The message originates in arrow-rs's
`value()` accessor, whose out-of-bounds assert is documented behaviour.
dataprof reaches it at `record_batch_analyzer.rs:107`, which calls arrow-rs's
`ArrayFormatter::value(row_index)`; for a dictionary column the formatter
resolves the key against the values array, and nothing between the C Data
Interface import and that call checks the key is in range. So the chain is:

```
abi-doctor produces dictionary<int8, utf8>, index 99, dictionary length 2
  -> arrow-rs from_ffi        accepts (import is zero-copy; full validation is opt-in)
  -> ArrayFormatter::value()  resolves key 99 against a 2-element StringArray
  -> panic, surfaced to Python as PanicException
```

This is an unvalidated-import observation rather than a defect in either
library taken alone, and reading arrow-rs makes that precise:

- `arrow_array::ffi::from_ffi` consumes the imported array, calls
  `align_buffers()`, and returns — it never calls `validate_full()`. The source
  notes validation is reachable only under `cfg(feature = "force_validate")`,
  tracked upstream in arrow-rs #10034.
- `ArrayData::validate_values()` **does** bounds-check dictionary keys, for
  signed key types included: `DataType::Int8 => self.check_bounds::<i8>(max_value)`.

So the check that would catch this already exists in arrow-rs; the FFI import
path simply does not invoke it. That makes the fix on the dataprof side a
single call — run `validate_full()` (or `validate_values()`) on FFI-imported
data before profiling it — rather than a new validator. Catching panics at the
pyo3 boundary would also stop a `BaseException` callers cannot catch from
escaping, but validating is the one that turns invalid input into a real error.

That arrow-rs accepts the array and pyarrow accepts it too, while a later
formatter call faults, is the exact shape this project is built to surface:
nothing rejects the input, and the consequence appears somewhere else.

**There is no pyarrow-only reproducer.** `pa.DictionaryArray.from_arrays`
bounds-checks and refuses to build the array (`Index 99 out of bounds`), so the
invalid input is unreachable from Python. Reaching it requires a producer that
comes in through the C Data Interface — which is the case this project exists to
make constructible, and is a fair illustration of why the gap it targets is real.

A secondary observation, not a bug claim: pyarrow **accepted** the same array on
C Data Interface import without complaint. Import is zero-copy and validation is
opt-in, so that is consistent with its documented behaviour — but it is a
concrete instance of two consumers disagreeing about the same bytes, which is
the shape M1 is built to find systematically.

**Resolved by [dataprof#610](https://github.com/AndreaBozzo/dataprof/pull/610)
(`0ca2766`), verified here.** dataprof now validates data arriving over the C
Data Interface and raises a `ValueError` naming the violated invariant instead
of letting an arrow-rs assert become a `PanicException`. The issue was filed as
an issue rather than a PR because the placement of an O(n) check on the hot path
was the maintainer's call; the merged fix validates at the analyzer, which keeps
a bounded profile bounded instead of validating a whole table up front.

Two things worth recording about how this one was verified.

**Only the harness can check it.** `pa.DictionaryArray.from_arrays`
bounds-checks, so `repro_findings.py` reports the case as unreachable from
Python and defers to `run_smoke.py`. The before/after evidence for finding 2 —
`PanicException` on 0.10.0, `ValueError` on `0ca2766` — exists only because a C
Data Interface producer can construct what Python refuses to. That is the
project's own argument for existing, and this is the first time it has been the
load-bearing one.

**The disagreement did not go away; it reversed.** dataprof now rejects the
array and pyarrow still accepts it. Before the fix both consumers took the data
and one of them faulted later. Neither state is a defect in pyarrow, and the
useful output of M1 is a matrix that records exactly this kind of split rather
than a verdict on either side.

## What M0.5 does not claim

- **Not a differential result.** Two consumers were used, but dataprof is a
  target we control and pyarrow ran to validate the instrument. Differential
  pairs start at M1, with a reference validator and a pre-declared coverage
  matrix.
- **No `CALLSEQ` execution.** The call sequence is still encoded and validated
  only; scripted lifecycle abuse is M1/M3.
- **No process isolation.** The harness catches a `PanicException` in-process,
  which is enough for a panic but not for a segfault. Worker isolation is a
  requirement for M1 and is not built yet — a consumer that truly crashes would
  still take this harness down.
- **The leak check had a blind spot in the harness.** `lifecycle()` is read
  after `release_all()`, but a consumer that takes the capsules and then fails
  without consuming them leaves live structures owned by the capsule, which are
  released later when Python collects it. That read as a leak at the moment of
  measurement even though nothing leaked. It did not arise in any run recorded
  here — the rejected runs never took a capsule, and the panicking run had
  already consumed them — so the figures above are unaffected.

  Fixed since (issue #6). The extension now counts capsules that have been cut
  and not yet destroyed, the report distinguishes **leaked** from **still held
  by the consumer**, and `run()` collects before measuring so that capsules
  reachable only from a dead consumer's object graph are gone by then. The
  counter that means "outstanding at this instant" is now named `outstanding`
  rather than `leaked`, so the two cannot be confused by reading the wrong key.
  `check_leak_accounting.py` guards the distinction and fails against the build
  that lacked it.
- **Buffer contents are native-endian data.** `.abicase` replays bytes exactly,
  so a case's *scalar values* only mean the same thing on hosts of the same
  endianness. Structure, topology and the encoding itself are architecture
  independent, and that is what the cross-architecture check verifies; the
  scalars are not, and that is a property of Arrow, not of the format.
